# План интеграции GUIDE в 1C-Битрикс

Это инструкция следующего этапа, а не отчёт о выполненной интеграции. Текущее поведение задано в `REQUIREMENTS.md`.

## Порядок работы для интегратора

1. Изучить настоящий шаблон `store_custom`, его header/footer, контейнеры и asset pipeline. В текущей папке есть только публичные снимки и подготовленная точка входа, нет установленного Bitrix. Завершение шага: названы фактические пути шаблона и каталог/торговые предложения.
2. Согласовать с владельцем сайта инфоблоки и поля для сущностей ниже. Завершение: стабильные коды сущностей и источник каждого поля документированы; ID не выдуманы.
3. Реализовать серверный адаптер, выдающий структуру версии 3 из `guide/assets/guide-data.js`. Завершение: PHP payload содержит реальные ссылки, медиаданные, дефолтный товар и все рекомендации; демо-файл остаётся только для автономного preview.
4. Подключить общий `guide.html`, изолированный CSS, локальный GSAP, motion и guide.js через asset pipeline в правильном порядке. Использовать штатные header/footer. Завершение: одна шапка/подвал, корректные URL `/guide/assets/…`, нет preview-shell CSS в production.
5. Проверить последовательность и матрицу из QA на staging. Добавить проверки доступности товара, пустых полей, кеша и внешних контейнеров реального шаблона. Завершение: отражённые в QA воспроизводимые результаты. Production-деплой выполнять только по отдельной явной задаче пользователя.

## Сущности и поля

| Сущность | Нормализованные поля / назначение |
| --- | --- |
| Настройки гайда | `settings.selectionMode = sequential`, `settings.requireAllGroups = true`, `settings.defaultProductId` |
| Дефолтный сценарий | `defaultRecommendation`: title, description, benefits, routines.morning / evening |
| Группа | id (стабильный код), title, hint, упорядоченные conditions |
| Состояние | id, label, description, more, signs[], image, imageAlt |
| Фактор | id, label, icon (имя разрешённого локального SVG) |
| Рекомендация | ключ состояния/фактора; title, description, benefits, productId, routines |
| Этап рутины | title, note, image; каждый шаг имеет собственную иллюстрацию |
| Товар | id, catalogId, name, image, imageAlt, detailUrl, buyUrl; реальные значения из каталога |

Дефолтный товар: создать административное поле/настройку со ссылкой на реальный элемент каталога. Редактор выбирает бестселлер вручную. ID выбранного товара преобразуется в ключ `products` и передаётся в `settings.defaultProductId`. Автоматический рейтинг по продажам не запрошен; его алгоритм, период, доступность SKU и кеш потребуют отдельного согласования. При пустой/неактивной настройке адаптер должен выдать согласованный безопасный fallback или состояние «товар не назначен», а не случайную карточку.

На фронтенде: незаполненные три группы → defaultRecommendation + настроенный товар. Все группы заполнены → отдельный контекст состояния/фактора и его productId. Не объединять состояния в одну рекомендацию при подготовке серверного JSON.

## Передача данных

Предпочтительный контракт: `script#tokatliann-guide-data[type=application/json]`, который имеет приоритет над demo JS. `guide/index.php` уже содержит безопасную сериализацию `JSON_HEX_*` и штатные подключения header/footer. Передать `$tokatliannGuideData` до вывода фрагмента; в реальном компоненте сформировать payload из `$arResult`. Проверить порядок относительно `guide.js`: он поддерживает запуск из head через DOMContentLoaded.

Имена и описания — plain text; renderer экранирует HTML. Коды — стабильные slug-и (латиница/цифры/дефис), поскольку участвуют в DOM ID/селекторах. URL — HTTPS или абсолютный путь от корня сайта; схемы javascript:, data:, обратные слеши и протокольно-относительные URL отклоняются. Сервер также проверяет типы, допустимые коды и ссылки. Пользовательский HTML не передавать.

## Кеш, каталог и продажи

Использовать штатный кеш компонентов/managed cache; инвалидировать при изменении настроек, контента гайда и привязанных товаров. Учесть активность элемента, доступность SKU, права доступа, URL торгового предложения и наличие изображения. Цена, наличие и покупка не должны подменяться статическими демо-значениями. Текущая «Купить» — переход к товару. AJAX-корзина, сессия и CSRF потребуют отдельной реализации.

## Медиа и автономный preview

В Bitrix контентные изображения поступают из файловых полей/каталога. Нужны оригиналы достаточного размера; не масштабировать кропы из макета. HTML-надписи остаются текстом, а маски/фейды — CSS. Поля image в состоянии и каждом шаге рутины делают иллюстрации заменяемыми из админки.

`preview.*`, `site-shell.css`, `work/`, корневой launcher и standalone index.html служат локальной демонстрации; не подключать их в шаблон сайта. После интеграции сохранить отдельный автономный набор данных, чтобы двойной клик продолжал работать. Реальные шрифты и оболочка берутся из действующего сайта.

## Проверки перед сдачей интеграции

Старт без выбранных состояний; блокировки 2/3; автооткрытие следующего шага; сброс зависимых ответов; выбранные факторы; раздельные рекомендации; дефолтный товар, изменённый в админке; оба периода рутины; пустые/неактивные товары; минимум прелоадера; reduced motion; быстрые клики; отсутствие зазора фото/футер на высоком desktop; mobile; отсутствие дублей шапки и конфликтов глобальных стилей. Отдельно проверить реальные браузеры и окружение Bitrix, которые локальная HTML-проверка не покрывает.
